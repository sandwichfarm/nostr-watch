**The styleguide must define each of these clearly:**

**Badge standards (FOUND-02):**
- Full badge set on every README: npm version, license, status (alpha/beta/stable), runtime support (web/node/deno/cli)
- Use shields.io badge URLs
- Provide copy-paste badge templates with placeholder values (`@nostrwatch/PACKAGE-NAME`)

**Code example format (FOUND-03):**
- No semicolons, single quotes, ESM imports matching `.prettierrc.yaml` conventions
- Import style: `import { X } from '@nostrwatch/package'`
- Use real relay URLs (e.g., `wss://relay.damus.io`) in examples
- Fenced code blocks with `ts` or `js` language tags
- Examples must be realistic and minimal — not trivial "hello world"

**Tone and voice (FOUND-04):**
- Newcomer-friendly: explain Nostr concepts briefly, link to relevant NIP specs
- Define terms when first used (relay, NIP, adapter, etc.)
- Do NOT assume prior Nostr ecosystem knowledge
- DO assume TypeScript/npm/pnpm familiarity
- Professional but approachable (not "alpha af" style from current auditor README)

**Known Limitations template (LIMIT-01):**
- Bulleted list format
- Each item describes: what the limitation is, why it matters, any workaround or planned fix
- Link to CONCERNS.md entry or relevant GitHub issue when available
- Honest but constructive tone — acknowledge tech debt without being alarming
- Provide a concrete example using a real concern from CONCERNS.md (e.g., the hardcoded MAX_FILTERS in route66)

**Deprecation stub template (LIMIT-02):**
- Prominent blockquote warning banner at very top: `> ⚠️ **DEPRECATED** — This package has been replaced by [X]. See [link].`
- Minimal stub below: why deprecated, where to go, no full API docs
- Provide concrete example for `apps/nocapd` (deprecated, replaced by relaymon)
- Note: `internal/nwcache` is also deprecated; `libraries/schemata` gets a redirect stub to `@nostrability/schemata`

**Package type variations:**
- The styleguide should note which sections are required vs optional per package type (app vs library vs internal)
- For example, "API" section is required for libraries, optional for apps
- "Prerequisites" required for apps (runtime, env vars), may be brief for internal packages

**Structure the styleguide itself with:**
- Introduction (what this document is, who it's for)
- Section Reference (each section with purpose, content expectations, and an example snippet)
- Badge Reference (templates)
- Code Example Guidelines
- Tone and Voice Guidelines
- Known Limitations Template
- Deprecation Stub Template
- Package Type Matrix (which sections required/optional per type)

**Configuration (from RESEARCH.md and CONTEXT.md decisions):**

```jsonc
{
  "config": {
    "default": true,
    "MD013": false,
    "MD034": false,
    "MD040": true,
    "MD001": true,
    "MD022": true,
    "MD024": { "siblings_only": true },
    "MD043": {
      "headings": [
        "*",
        "## Overview",
        "*",
        "## Installation",
        "*",
        "## Quick Start",
        "*",
        "## Known Limitations",
        "*",
        "## License"
      ],
      "match_case": false
    }
  },
  "globs": [
    "libraries/*/README.md",
    "apps/*/README.md",
    "internal/*/README.md"
  ],
  "ignores": [
    "node_modules/**",
    "**/CHANGELOG.md"
  ]
}
```

**Key decisions:**
- `MD013: false` — line length too noisy for README prose
- `MD034: false` — bare URLs too noisy with badge service URLs
- `MD040: true` — fenced code blocks MUST have language tags (FOUND-03)
- `MD043` — enforces required sections in order with `"*"` wildcards allowing optional sections between required ones
- `globs` scoped to package READMEs only — avoids linting `.planning/`, `docs/`, scripts
- `ignores` excludes node_modules and CHANGELOG files (non-conforming heading structures)

**After creating the file, verify it works:**
Run `npx markdownlint-cli2 --help` to confirm the tool is available. Do NOT run it against actual READMEs yet (they don't exist/conform yet).

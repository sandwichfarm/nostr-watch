## Summary

Phase 4.1 addresses three discrete integration debt items identified by the v1.0 milestone audit. All items are documentation fixes or metadata additions; no source code changes are required. The work is surgical: one broken relative link, adding `###` subheadings to CONCERNS.md for each concern referenced by anchor fragment, and adding a `nostrwatch` metadata block to `apps/nocapd/package.json`.

The phase is small-scope with well-understood root causes. Each fix has a single correct implementation with no meaningful alternative approaches. The main planning risk is accurately cataloguing the exact anchor fragment slugs needed and the exact CONCERNS.md location for each new subheading.

**Primary recommendation:** Fix in three sequential tasks — broken link first (CI blocker), then CONCERNS.md anchors, then nocapd metadata.

## Architecture Patterns

### Fix 1: Broken Link (INT-09)

**File:** `internal/seed/README.md`, line 167

**Current (broken):**
```markdown
- [`@nostrwatch/db`](../../internal/db/README.md) — provides the SQLite database...
```

**Fixed:**
```markdown
- [`@nostrwatch/db`](../../libraries/db/README.md) — provides the SQLite database...
```

**Why it broke:** The `db` package lives in `libraries/db/`, not `internal/db/`. There is no `internal/db/` directory. The relative path from `internal/seed/README.md` to `libraries/db/README.md` is `../../libraries/db/README.md`.

**Path verification:**
- `internal/seed/README.md` is at depth: `internal/seed/`
- `../../` resolves to the monorepo root
- From root: `libraries/db/README.md` is correct
- `libraries/db/` exists and has a `README.md` (confirmed)

**CI impact:** lychee checks all `internal/*/README.md` files and fails on PR. This is a blocking CI failure for any PR that touches this file.

### Fix 2: CONCERNS.md Anchor Fragments (LIMIT-01)

**Problem:** READMEs link to `CONCERNS.md#some-slug` but CONCERNS.md only has top-level `##` section headings, not `###` concern-specific subheadings. GitHub/VitePress anchor slugs are computed by lowercasing the heading text and replacing spaces with hyphens.

```

## Known Bugs
## Security Considerations
## Performance Bottlenecks
## Fragile Areas
## Scaling Limits
## Dependencies at Risk
## Missing Critical Features
## Test Coverage Gaps
```

| `#default-relay-configuration` | `### Default Relay Configuration` | `## Tech Debt` |
| `#incomplete-rtt-extraction` | `### Incomplete RTT Extraction` | `## Tech Debt` |

**Critical finding:** The two relaymon anchor fragments both link to `#known-bugs` — this anchor slug resolves correctly to the existing `## Known Bugs` heading. The audit's "7 broken anchors across 5 READMEs" count includes relaymon, but relaymon's 2 links are to `#known-bugs` which already exists. The actual broken anchors are 9 unique slugs across 4 files (route66: 3, auditor: 1, gui: 3, rstate: 3), but relaymon's 2 links already work.

**Recommendation:** Confirm relaymon links resolve before planning — if they do, only 9 anchors need fixing, not 11.

**Implementation approach:** Convert each bold-text concern entry in CONCERNS.md into a `###` subheading. The existing bold text (`**Hardcoded Filter Limits:**`) maps to the heading text needed (`### Hardcoded Filter Limits`). The body content under each bold entry is unchanged.

**Example transform for one concern:**

Current in CONCERNS.md:
```markdown

```

After fix:
```markdown

- Issue: MAX_FILTERS hardcoded as 10 with TODO in...
```

**Scope of changes to CONCERNS.md:** Only the affected `###`-level headings need to be added. The `##` section structure is preserved. The concern body text is unchanged.

### Fix 3: PackageIndex Metadata (FOUND-08 + LIMIT-02)

**Problem:** `docs/.vitepress/packages.data.ts` reads `pkg.nostrwatch?.deprecated ?? false` and `pkg.nostrwatch?.status ?? 'alpha'` from each package's `package.json`. No package currently defines the `nostrwatch` key, so:
- All packages show as `alpha` status
- No package shows as deprecated in the discovery index

**PackageIndex.vue behavior (confirmed from source):**
- `deprecated: pkg.deprecated` — adds `.deprecated` CSS class (opacity 0.6, strikethrough on name)
- `status-badge` shows `'deprecated'` text with red background when `pkg.deprecated` is truthy

**Minimum viable fix:** Add to `apps/nocapd/package.json`:
```json
"nostrwatch": {
  "deprecated": true
}
```

This is a JSON addition inside the existing `package.json` root object.

**Current `apps/nocapd/package.json`** — it is a valid JSON file with no `nostrwatch` key. The field can be added anywhere in the root object; conventional placement is after `"license"` or at the end before the closing `}`.

**What the audit recommends:** "Minimum viable fix: Add `"nostrwatch": { "deprecated": true }` to nocapd and nwcache `package.json`". The audit mentions `nwcache` as well, but the phase success criteria specifies only `apps/nocapd/package.json`. Stick to the success criteria; nwcache can be addressed in a follow-on phase if needed.

**Why not also add `status` field:** The `status` field is an enhancement (shows `alpha` by default which is fine for most packages). Adding `status` to all packages is FOUND-08 enhancement scope but not required for this phase. The phase success criteria only requires nocapd shows as `deprecated`.

## Common Pitfalls

### Pitfall 1: Wrong heading level for CONCERNS.md entries
**What goes wrong:** Adding `##` headings instead of `###` headings. GitHub slugifies `## Hardcoded Filter Limits` as `#hardcoded-filter-limits` the same as `### Hardcoded Filter Limits`, so functionally either works for anchor resolution. However, using `###` is semantically correct — these are sub-items under the `##` section headings.
**Why it happens:** CONCERNS.md currently only has `##` headings, so the temptation is to continue that pattern.
**How to avoid:** Use `###` for concern entries. The `##` headings are category sections; `###` headings are individual concerns.
**Warning signs:** If you write `## Hardcoded Filter Limits` (two hashes), you're changing the document's section structure.

### Pitfall 2: Wrong relative path for seed README link
**What goes wrong:** Using `../libraries/db/README.md` (one `..`) instead of `../../libraries/db/README.md` (two `..`).
**Why it happens:** Miscounting depth. The file is at `internal/seed/README.md`.
**How to avoid:** Count: `internal/seed/README.md` → `../../` goes to the monorepo root → `libraries/db/README.md`. Always verify with `ls` from the file's directory.
**Warning signs:** Lychee still fails after the fix.

### Pitfall 3: JSON syntax error in package.json
**What goes wrong:** Adding `nostrwatch` block without proper comma separation from adjacent keys, or with a trailing comma.
**Why it happens:** JSON is strict about commas.
**How to avoid:** Add the block after the last existing key-value pair before the closing `}`, or before an existing key with a trailing comma. Validate with `node -e "require('./apps/nocapd/package.json')"` after editing.
**Warning signs:** VitePress dev server crashes on data loader parsing error.

### Pitfall 4: Assuming relaymon links are broken
**What goes wrong:** Spending time "fixing" relaymon's `#known-bugs` links which already resolve.
**Why it happens:** The audit says "7 CONCERNS.md anchor fragments across 5 READMEs" and lists relaymon as one of the 5.
**How to avoid:** Verify: `## Known Bugs` exists in CONCERNS.md → its anchor slug is `#known-bugs` → relaymon links already resolve correctly. No change needed to relaymon's README.
**Warning signs:** N/A — if you verify before editing, you won't touch relaymon unnecessarily.

### Pitfall 5: Modifying CONCERNS.md heading titles vs. adding `###` entries
**What goes wrong:** Renaming the existing `## Tech Debt` section or restructuring CONCERNS.md significantly.
**Why it happens:** CONCERNS.md has bold-text entries that function as informal sub-headings. It's tempting to also clean up other formatting.
**How to avoid:** Only convert the specific bold-text entries that correspond to broken anchor fragments into `###` subheadings. Leave everything else unchanged.
